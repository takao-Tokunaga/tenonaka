# 波びん 要件定義書

## テーマ

ハッカソンテーマ:**「AIにできないこと」**

## 設計の出発点

### 弱い答えと強い答え

「AIにできないこと」を探すとき、**「AIのほうが下手なこと」に逃げてはいけない**。
文章の質、感情の機微、創造性 — どれも「来年には追いつく」で論破される。

強い答えは **構造的に不可能なこと**。上手い下手ではなく、定義上そのものになれないこと。
その中で、スマートフォンが**検証できる**ものは限られる。

### 判定基準

設計案の強度を測るために、次の問いを使った。

> **このアプリを、AIエージェントは使えるか?**

「主観的なことを記録するアプリ」はどう作ってもこの問いに **使える** と答えてしまう。
入力欄がある限り、AIがフォームを埋められるからである。
したがってテーマはコンテンツではなく **機構** に宿す必要がある。
身体を持つ人間しか通れない関門を作る、ということ。

### 選んだ関門

| 行為 | 要求されるもの | AIに存在しないもの | 証明の強さ |
|---|---|---|---|
| **送る** | 指を当てて脈が測れること | 脈(灌流のある生体組織) | 強い |
| **読む** | 端末を握り続けること | 手(生理的微動) | 中程度 |

コストと証明の強さが行為の重さと釣り合っている。
取り返しのつかない「送る」には数秒かかる強い証明を、継続が本質の「読む」には
摩擦ゼロの弱い証明を割り当てた。

### 何を希少と見たか

2026年に希少なのは知能ではない。文章・画像・レビュー・返信・人格は無限に生成できる。
**再生数も滞在時間もいいねも偽装できる。**

無限に生成できないのは人間の身体である。
だから本アプリが記録するのは、内容の良さではなく **費やされた身体の時間** とした。

## コンセプト

**生きた手に握られている間だけ、文字が現れる便り。それを宛先の無い海に流す。**

AIの代表的な仕事は要約である。長いものを短くし、読まずに済ませる。
本アプリは **要約されることを構造的に拒む文章** を成立させる。

遺言、長い謝罪、離れた人への言葉 — 要約されるべきでないものがある。
それを形として保証する。

宛先を持たせないのは、**言えない相手にしか言えないことがある**からである。
特定の誰かに宛てると言えなくなる言葉を、見知らぬ誰かへ向けて置けるようにする。

## 体験の核

- 便りは**手に持っている間だけ**進む。机に置くと止まり、拾い上げると再開する
- **まだ現れていない文字は描画しない。** 先を覗くこともスクリーンショットで
  先取りすることもできない。便りの長さも分からないので、残りを推し量れない
- 流した人に返るのは内容への返信ではなく、**流した脈 → 読んだ脈**と
  生きた手が握っていた時間である
- **一通も流していない人は拾えない。** 受け取るだけの海にしない
- 拾った便りは**一人にしか渡らない**。同じ便りが二人に読まれることはない

## 画面構成

1. **入口(海)**
   画面の3割から下が海。漂っている便りの数だけ瓶が浮かぶ。
   海の中に「海に流す」を置き、**拾うのはボタンではなく浮かんでいる瓶をタップする**。
   過去の記録は主役ではないので、隅の「棚」に畳む

2. **書く画面**
   本文だけ。**宛名も署名も持たない**(宛先の無い海に流すので要らず、
   名乗らないことがこの海の匿名性そのもの)

3. **封をする画面**
   背面レンズに指を当てる。当て方の失敗は原因を判別して指示を返す。
   脈が2秒安定すると封が押され、朱印に拍数が入る

4. **流す演出**
   紙が巻かれ、瓶に入り、栓がされ、水面に浮かんで流れていく

5. **拾う演出**
   波の向こうから瓶が流れてくる。手元で立ち、栓が抜け、中の便りが出て開く

6. **読む画面**
   握っている間だけ毎秒10文字ずつ現れる。置くと止まり、静かに理由を出す。
   最後まで現れたら、今度は**自分の脈で封をして返す**

7. **棚**
   拾った便りと流した便りの記録。**拾った便りの本文は手元に持たない**ので、
   読み直すときもサーバーから取り直し、もう一度握ることになる

## 機能要件 (MVP)

| # | 機能 | 内容 |
|---|------|------|
| 1 | 便りの作成 | 本文のみ。宛名・署名を持たない |
| 2 | 脈による封印 | 背面カメラで PPG を測り、拍数を便りに刻む。**脈が無いと流せない** |
| 3 | 海に流す | 宛先を持たない。誰に届くかは決められない |
| 4 | 海から拾う | 浮かんでいる瓶をタップする。**一通流していないと拾えない**(相互性) |
| 5 | 一人にしか渡らない | 拾われた便りは海から消える。同時に拾おうとしても片方だけが取る |
| 6 | 保持中のみの開示 | 手の微動を検出し、握られている間だけ文字を現す |
| 7 | 未開示部分の非描画 | 現れていない文字は描画しない |
| 8 | 読み手の脈で返す | 読み終えたら自分の脈で封をする。流した人に届く |
| 9 | 読了報告 | 握っていた時間・置かれた回数・読了したかを流した人に返す |
| 10 | 棚 | 拾った・流した記録。本文は持たず、符号だけを保管する |
| 11 | 接続先の変更 | タイトル長押しで実行中に差し替え(会場対策) |

### スコープ外

- プッシュ通知(拾われたことをその場で知らせない)
- 内容への返信機能(**意図的に持たない**。返るのは身体の事実だけという設計)
- 検索・一覧の共有
- 特定の相手を指定して送ること(**海であることを壊すため持たない**)
- 便りの削除・取り消し(流したものは戻らない)

## 計測仕様

### 脈 — 光電容積脈波 (PPG)

指を透過した光は、心臓が血を送るたびに毛細血管の血液量が変わることで
赤成分の平均値が上下する。これを心拍として拾う。

| 項目 | 値・方針 |
|---|---|
| 取得 | AVFoundation、`sessionPreset: .low`、30fps 固定、BGRA |
| 解析対象 | 中央 ROI の赤成分の平均(4px 間引き) |
| 前処理 | 1秒の移動平均を引く(ハイパス)→ 0.10秒の移動平均(ローパス) |
| 拍の検出 | 不応期 0.30 秒(= 最大 200bpm)、閾値は RMS の 0.5 倍 |
| 心拍数 | 拍間隔の**中央値**から算出(外れ値に強い) |
| 確からしさ | 拍間隔のばらつきと本数から 0〜1。0.5 以上で採用 |
| 露出 | 指が乗って 0.8 秒後に**固定**。自動のままだと血液量の変化を補正で打ち消す |
| ライト | **既定は消灯**。光量不足を2秒判定してから弱く点灯(0.1)し、必要なら自動で上げる |
| 封の確定 | 良好な状態が 2 秒続いたとき |

**当て方の指示**は状態から判別して返す。押しつけすぎ(灌流が止まって波形が平坦)が
最も多い失敗なので、振幅÷明るさ(灌流指数)で判定している。

### 微動 — 生理的微動 (8〜12Hz)

人間の手には運動単位の発火に由来する 8〜12Hz の不随意な震えがある。
机に置いた端末には存在しない。

| 項目 | 値・方針 |
|---|---|
| 取得 | CoreMotion `deviceMotion` を 100Hz。加速度(重力除去)と角速度の大きさ |
| 解析 | 1秒窓 + ハン窓 → **Goertzel 法**で 8〜12Hz を 1Hz 刻みに直接計算 |
| 判定信号 | `max(加速度帯域, 角速度帯域 × 0.2)` |
| しきい値 | **0.0013** |
| ヒステリシス | 離す判定のみ **1.5秒遅延**。再開は即時(非対称) |

iPhone 15 での実測値:

| 条件 | 8〜12Hz の強さ | 「置く」比 |
|---|---|---|
| 手に持つ | 0.00352 | 23倍 |
| 机に肘をついて構える | 0.00184 | 12倍 |
| 持って歩く | 0.02512 | 167倍 |
| 机に置く | 0.00015 | — |

しきい値 0.0013 は「置く」の **8.7倍上**、「机に構える」の **1.4倍下**。

当初は 0.0008 / 3秒遅延だったが、**置いたつもりで判定が続く**ことがあったため厳しくした。
3秒の遅延は「置いたのに文字が出続ける」として体感に出る。1.5秒あれば持ち替えは吸収できる。
これ以上しきい値を上げると「机に肘をついて構える」= 正当な読み方が止まりはじめるので、
ここが上限に近い。

**「机に手をついて構えたときに置いたと誤判定しないか」** が設計時の最大の懸念だったが、
実測で 12 倍の差が出たため解消した。

### 使わないもの

推論を使うとテーマそのものを損なうため、以下は使用しない。

- **HealthKit**(心拍を借りない。Apple Watch 不要でも動くという利点もある)
- **Vision / CoreML**(オンデバイス推論も AI である)
- **LLM・生成系 API**

心拍数はカメラの生のピクセルから自分で計算しており、
外部通信は自前のサーバーに対してのみ発生する。

## データ設計

```prisma
model Letter {
  id           String   @id @default(uuid())
  code         String   @unique   // UI には出さない。読み直しの取得に使う
  body         String
  senderBpm    Float?             // 流した瞬間の脈
  senderUserId String
  sentAt       DateTime @default(now())

  claimedByUserId String?         // 拾った端末。null のあいだが「まだ海にある」
  claimedAt       DateTime?

  readHeldSeconds  Float?         // 生きた手が握っていた秒数
  readReleaseCount Int?           // 途中で置かれた回数
  readCompleted    Boolean?
  readReaderBpm    Float?         // 読み終えたときの読み手の脈
  readAt           DateTime?

  @@index([senderUserId, sentAt])
  @@index([claimedByUserId, sentAt])   // 海から拾うときに引く
}
```

設計の要点が3つスキーマに出ている。

**`claimedByUserId` が null かどうかが「海にあるか」である。** 別のテーブルを持たず、
1つの列の有無で海の状態を表している。索引もこの列に張っている。

**内容への返信の置き場が無い。** 返るのは `readReaderBpm` `readHeldSeconds`
`readReleaseCount` — すべて身体の事実である。返信を持たない方針を、
機能で禁じるのではなくスキーマの段階で表現している。

**脈が2つある。** `senderBpm` と `readReaderBpm`。このアプリが返すものは
「流した身体から、読んだ身体へ」であり、それが列として並んでいる。

なお `senderName` `recipientName` の列は残しているが、**アプリからは書き込まない**
(宛名と署名を捨てたため)。列を落とす移行を打つより、使わない列として残す判断をした。

## API 設計

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/letters` | 海に流す。`senderBpm` 必須 |
| POST | `/letters/pickup` | 海から一通拾う。**流した実績が無ければ拒否** |
| GET | `/letters/sea` | 海の通数と、自分が拾える数 |
| GET | `/letters/sent` | 流した便りと、その読まれ方 |
| GET | `/letters/received` | 拾った便りの控え。**本文を返さない** |
| GET | `/letters/:code` | 符号で本文を取る(読み直し用) |
| POST | `/letters/:code/receipt` | 読まれ方を返す |
| GET | `/health` | 死活確認 |

- **`senderBpm` を必須にしている**のが要点。関門をクライアント側の実装に
  委ねず、API の契約として表現している
- **拾うときは相互性をサーバーで確かめる。** 「流した数 > 拾った数」でなければ拒否する。
  クライアントがボタンを押せるかどうかの判定に任せていない
- **`/letters/received` は本文を返さない。** 手元に全文が残ると、
  握らないと読めないという機構が読み直しで崩れるため
- 読了報告は上書きではなく、**より長く握られた記録が残る**。読み直しで時間が減らないため
- レート制限は 60 回/分。本文は 20,000 字、脈は 25〜220 の範囲外を拒否する
- 符号の生成には `crypto.randomInt` を使う。符号は読み直しの鍵として機能するので、
  予測可能な `Math.random()` を使ってはいけない

### 一人にしか渡らないことをどう担保するか

拾う操作は、**条件つきの UPDATE 一本**で表している。

```
UPDATE Letter
   SET claimedByUserId = :me, claimedAt = now()
 WHERE id = :選んだ便り
   AND claimedByUserId IS NULL      -- ここが要点
```

更新件数が 0 なら、他の誰かに先を越されたと判断してやり直す。
楽観ロックで済むので、キューや排他の仕組みを足す必要がない。
**「同時に2人が同じ瓶を拾ったらどうなるか」への答えがこの1行である。**

### 符号は「言える言葉」であるべき

符号は当初、声に出して相手に渡すものだった。海に流す形に変えたので**渡す相手がいなくなり、
UIからは消えた**が、読み直しの鍵として残っている。読める言葉である必要はもう無いが、
ログや障害対応で人が扱う値なので、読める形を保っている。

| | DBのパスワード | 符号 |
|---|---|---|
| 読む相手 | 機械だけ | 人 |
| 声に出すか | 出さない | 出しうる |
| あるべき姿 | 意味のない最大乱数 | **言える言葉** |

仮名の音節(58種)を5つ並べた10文字として発行する。`MISUHABOGI` はそのまま読めるが、
`2UJECG` は「にーゆーじぇいいーしーじー」となり、人が扱う値にならない。数字を使わないので
`I/1` `O/0` の見間違いも起きない。

58<sup>5</sup> = 約6億5000万通り。英数字6文字(約10億通り)よりエントロピーは下がるが、
総当たりへの本当の守りは「一度しか渡らない」機構のほうにある。

## 技術構成

- **iOS**: Swift / SwiftUI。紙の質感と明朝体(Hiragino Mincho)
  - 紙の粒子は起動時に一度だけノイズ画像を生成してタイル敷き
- **バックエンド**: NestJS + Prisma + PostgreSQL
- **本番**: AWS App Runner (0.5 vCPU / 1GB) + RDS PostgreSQL 18.3 (db.t4g.micro / gp3 20GB)
  - リージョン ap-northeast-1。App Runner → VPC コネクタ → RDS(非公開)
  - DB の接続情報は SSM SecureString。**App Runner の環境変数には置かない**
    (`describe-service` で誰でも平文で読めるため)
  - **App Runner を選んだ理由は HTTPS**。会場で他人の端末に入れるので、証明書の警告が
    出る構成は使えない。ALB と Elastic Beanstalk は ACM 証明書=自前ドメインが必要。
    Lambda + API Gateway なら HTTPS は得られるが、Prisma の初期化がコールドスタートに乗り、
    RDS への接続数を抑えるには RDS Proxy(月額増)が要る。**同じ Dockerfile が
    ローカルでも本番でも動く**ことを取った
  - 月額は約28ドル(RDS $18.25 / App Runner メモリ $6.46 / ストレージ $2.76)。
    内訳と削るために決めたことは [README](../README.md#コストが考えられているか) に書いた
- **認証**: 簡易実装。端末ごとに発行した UUID を `x-user-id` で送る。
  **自己申告なので、他人の UUID を名乗ればその人の控えが見える。**
  身内のデモを想定した水準であり、広く配るなら塞ぐ必要がある

## 正直な限界

デモの場で問われうる点を先に整理しておく。

| 指摘 | 回答 |
|---|---|
| 別の端末で撮影して要約できる | できる。技術的に防げない。この機構が保証するのは「防止」ではなく **「費やされたかどうかの申告」** である |
| 人を雇えば投稿・読解できる | できる。**ボットを不可能にするのではなく、1件のコストを「人間の身体1回ぶん」に固定する**のが正確な効果。計算資源では買えないコストにする |
| 誰が読んだかは証明できるのか | できない。脈は個人識別に使えない(常に変動し、他人と重なる)。証明できるのは「生きた身体がその瞬間そこに居たこと」まで |
| 波形の録画を再生されたら | 理屈上あり得る。今回は対策していない |
| 心拍数の精度は | 妥当な値が出ることを確認しただけで、正解と突き合わせた検証はしていない。**医療的な測定として提示しない** |
| 微動は偽装できないのか | バイブレーターで偽装しうる。脈より弱い証明である |
| 握る仕掛けはサーバーが守っているのか | **守っていない。** 文字を現す判定は端末側にあり、改造した端末なら本文を一度に取れる。これは体験の機構であって認可の境界ではない。サーバーが担保しているのは「一通流さないと拾えない」「一人にしか渡らない」の2つだけである |
| 海が空だったら | 拾えない。デモ前に種を入れる([scripts/seed-sea.sh](../scripts/seed-sea.sh))。便りは一人しか拾えないので、試すたびに減る |
| 誰かの便りが不快な内容だったら | 通報も削除も持っていない。**広く配るなら必要になる**が、今回は入れていない |
| DB が壊れたら | 戻らない。単一AZ・バックアップ保持0日で運用している。保持を7日にするのは追加費用がほぼ無いので、デモ後に上げるべき点として認識している |

## 検討過程で不採用とした案(参考記録)

到達順に記録する。いずれも「AIにできないこと」の答えを探す過程で出た。

### 1. 香りのしおり(匂いの日記)

匂いを感じた瞬間の記憶を日記にしおりとして挟む案。実装まで進めたが不採用。

**理由**: テーマを「不在」で表現していた。「AIを使っていない」は実装の性質であって
体験ではなく、審査員には見えない。また匂いはコンテンツにすぎず、「音」や「天気」に
差し替えても構造が変わらないため、日記アプリに項目が増えただけに見えた。
上述の判定基準に照らすと **AIがフォームを埋められてしまう**。

紙と明朝体の世界観、および PPG の実装はここから引き継いでいる。

### 2. 心臓がしおりを挟む案

書いたあと脈で封をし、平常値より上がっていたらアプリが黙ってしおりを挟む案。

**理由**: 心拍の上昇を「興奮」と解釈した瞬間、感情判定という AI と同じ土俵に乗り、
しかも精度で負ける。「理由を判定せず事実だけ残す」形に整えれば成立するが、
日記という器から離れられていなかった。

### 3. 問いの本

問いが1つ現れ、読むだけで何も入力せず、心臓が反応した問いだけが残る案。
入力欄がゼロになるため判定基準は満たしていた。

**理由**: 脈が問いに反応するかの信頼性が低く、外れると占いになる。
また問いの在庫が有限で、使い込むと尽きる。

### 4. 人間だけが投稿できる場所

生きた心臓がないと1文字も投稿できない掲示板。壁に文章と心臓の線が並ぶ案。

**理由**: 案として有力で保留扱い。ただし「AIに書かせた文章を人間が送る」で
主張が破れるため、言えることが「AIだけでは1件も投稿できない」に限定される。
手紙のほうが**要約という AI の代表的な仕事に正面から答えられる**ため今回は見送った。

### 5. その他の身体計測

| 手段 | 判断 |
|---|---|
| 息(マイク) | 摩擦が低く表現力もあるが、扇風機やスピーカーで偽装でき証明が弱い |
| 気圧(高度変化) | ソフトウェアで偽装不可能だが遅く、ステージで見せられない |
| 胸に載せて心拍(心衝動記録) | 皮膚に触れず測れて派手だが、寝転がる必要がある |
| TrueDepth の顔形状 | 証明は強いが ARKit の顔認識=推論を使うことになり、テーマを損なう |
| Apple Watch の心電図 | 生々しいが、審査員に渡せないためデモに向かない |
| タップのゆらぎ | 生成モデルで人間らしい揺れを模倣できるため証明にならない |
